# Task E (bonus) — оберіть ОДИН шлях

## Шлях 3 — план виведення старого модуля з експлуатації

План заміни спільного форматера на явні форматери для кожного споживача
(strangler fig), **кроками, кожен з яких безпечно випускати окремо**:

1. Створити нові специфічні функції у `lib/format.js`: `formatDateAccounting`, `formatDateInvoice`, та `formatDateReminder`. На цьому етапі їхня реалізація є ідентичною або просто викликає старий `formatDate`. Зареєструвати їх в `module.exports`.
2. У файлі `config/export-columns.json` замінити тип "Date" на "DateAccounting" (щоб він викликав `format['formatDateAccounting']`). Випустити зміни, переконавшись, що експорти для бухгалтерії працюють.
3. Оновити файл `invoices/render.js` для використання нової функції `formatDateInvoice` замість загальної `formatDate`. Випустити зміни, переконавшись, що рахунки генеруються коректно.
4. Оновити файл `notifications/reminders.js` для використання нової функції `formatDateReminder`. Випустити зміни.
5. Після того, як усі споживачі перейшли на специфічні методи, реалізація кожного методу може змінюватися незалежно (наприклад, `formatDateInvoice` переводиться у формат DD.MM.YYYY, а `formatDateAccounting` залишається незмінним).
6. Видалити стару функцію `formatDate` з кодової бази, оскільки на неї більше ніхто не посилається.

**Що на кожному кроці захищає від регресії:**
Наявність характеризаційних тестів (для HTML рахунків, нагадувань і CSV експорту), які фіксують очікуваний вихід для кожного зі споживачів. Поступовий (покроковий) перехід споживачів дозволяє звузити обсяг можливих помилок при кожному деплої, і тести забезпечують, що під час зміни точки виклику формат залишається незмінним.
